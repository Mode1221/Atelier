# Usertest — AI 대리 사용성 테스트

목표: 사람을 모으기 전에 **치명·높음 사용성 문제를 0으로** 만든다. 실제 사용자 검증은 이어지는 공개 베타(`atelier:beta`)가 맡는다.

## 원리
- 실행기 `scripts/walk.mjs` 는 요소를 **화면에 보이는 이름으로만**(역할·라벨·글자) 찾는다. 코드 선택자를 쓰지 않는다 → 못 찾으면 사용자도 못 찾는다.
- 한 단계에 5초 안에 못 찾으면 "막힘". 화면마다 자동 점검: 가로 넘침, 터치 영역(24px 미만 높음 / 44px 미만 낮음), 이름 없는 입력칸, 콘솔 오류, axe(있으면).
- **기대 단어**: 페르소나가 화면을 보기 전에 "이 일을 하려면 무슨 말을 찾을지" 먼저 적는다. 화면에 그 말이 없으면 "부분" — 라벨이 사용자 말과 다르다는 신호.

## 단계
### U1. 페르소나 3~5명 (`docs/idea.md` 대상 사용자에서)
반드시 섞는다: 핵심 사용자 / **다른 말을 쓰는 사람**(나이·업계가 다른) / 운영자가 아닌 쪽(공유 링크로 들어온 사람 등) / 데스크톱·다크 모드. 게임이면 장르 초보.

### U2. 과제 3~6개 (`docs/spec.md` 스토리에서)
목표만 적는다("~해 보세요"). 과제 전 상태가 필요하면 `setup` 단계로 만든다(시간·결과에 안 들어감).

### U3. 기대 단어 → 계획 파일
**화면·코드를 보기 전에** 페르소나별 `words` 를 적고, 그다음 코드를 보고 `steps` 를 쓴다. 형식은 `references/plan-format.md`. 파일: `docs/usertest/plan.json`.

### U4. 실행
```
node <atelier>/skills/usertest/scripts/walk.mjs docs/usertest/plan.json docs/usertest/<날짜>
```
- 로컬 서버를 띄워 실행한다(운영 DB 오염 금지). IP 기준 속도 제한이 있으면 `"ipHeader"` 로 방문자를 나눈다.
- playwright 가 없으면 `npm i -D playwright` (무료). 결과: `summary.md`, `results.json`, `shots/`.
- **스크립트가 기본이다.** playwright-mcp(대화형 브라우저)는 PROJECT.md "디자인 도구 계획"의 usertest 칸에 있을 때만, 스크립트로 못 찾는 막힘 탐색·재현이 어려운 레이아웃 버그 추적에만 쓴다. 모바일 네이티브는 쓰지 않는다.

### U5. 관찰자 검토 (AI)
`shots/*-end.jpg`·`*-stuck.jpg` 를 **페르소나 눈으로** 본다. 질문은 `references/observer.md`:
5초 안에 무엇을 하는 화면인지 알겠나 · 다음 할 일이 보이나 · 중요한 게 스크롤 아래에 묻혀 있나 · 쓰일수록(데이터가 쌓일수록) 나빠지는 배치인가.

### U6. 보고서·수정·재실행
`docs/usertest/<날짜>.md` 에 발견 표(심각도·근거·조치). 치명·높음은 **바로 고치고** U4 재실행. 테스트 코드(E2E)도 같이 돌린다 — 라벨 변경이 접근성 이름 충돌을 만들 수 있다.

### U7. 자동화 (권장)
프로젝트에 `npm run usertest`(로컬 서버 + 실행기) 를 만들고 CI 에 넣는다. 매 변경마다 과제가 여전히 되는지 확인되고 결과가 CI 요약에 붙는다. 예: `examples/beolgeum-jangbu/scripts/usertest.sh`, `.github/workflows/beolgeum.yml`.

## 판정
- 통과: 실패 0, 부분은 검토 완료, 자동 점검 높음 0 → launch L1 완료, **공개 베타로 간다**.
- 사람 5명 테스트는 선택. 대신 베타 피드백 20건을 L1 보완 근거로 쓴다.

## 한계 (보고서에 적는다)
동기·가치(정말 쓰고 싶은가), 실제 손·기기·시력, 사회적 맥락(단톡방 공유) 은 못 본다 → 베타 지표와 피드백으로.

## 산출물
