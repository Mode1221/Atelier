# 서비스 목표치(SLO)·오류 예산·장애 관리

"잘 돌아가나?"를 느낌이 아니라 **숫자 하나**로 판단하고, 그 숫자로 "기능을 더 만들까, 안정화할까"를 정한다. 1인 운영 기준으로 줄였다.

## 1. 무엇을 잴까 (SLI)
| 지표 | 재는 법 (무료 스택) | 기본 목표 (SLO) |
|---|---|---|
| 가용성 | 정기 점검·지킴이의 `/health` 성공 비율 (매시간 또는 5분) | 월 99.5% (≈ 월 3.6시간까지 다운 허용) |
| 핵심 흐름 성공률 | 배포 스모크 + 운영 E2E(선택) 성공 비율, 또는 서버 로그의 핵심 API 2xx 비율 | 99% |
| 응답 속도 | 핵심 화면 p95 (bench·Workers 분석) | spec S5 숫자 (예: 1초) |
| 오류율 | 5xx ÷ 전체 요청 (`request_failed` 이벤트) | 1% 미만 |
목표는 **spec S5 와 같은 숫자**로. 처음부터 99.9% 를 약속하지 않는다(무료 등급·1인 운영에 맞지 않음).

## 2. 오류 예산
- 예산 = 1 − 목표. 99.5% 면 한 달에 0.5% (약 3.6시간)까지 "망가져도 되는" 몫.
- **예산을 절반 넘게 쓰면**: 그달 새 기능 배포를 멈추고 원인 제거·테스트·모니터링 보강만 한다 (grow 기능 사이클 보류).
- 예산이 남으면: 실험·큰 변경을 해도 된다.
- 매월 1일 `docs/operations.md` "SLO 기록"에 지난달 가용성·오류율·예산 사용률 한 줄 (checkup monthly 가 채운다).

## 3. 장애 등급 (혼자 운영 기준)
| 등급 | 뜻 | 예 | 대응 |
|---|---|---|---|
| SEV1 | 서비스 전체가 안 되거나 데이터·개인정보가 위험 | 사이트 다운, 남의 데이터가 보임, 비밀값 유출 | **즉시**: 롤백·점검 모드 → 공지 → 원인. 개인정보면 guard 신고 기준 확인(72시간) |
| SEV2 | 핵심 흐름 일부가 안 됨, 우회 가능 | 결제·가입 실패 증가, 특정 기기 오류 | 당일: 원인 찾기 → 수정 배포 |
| SEV3 | 불편·일부 기능 | 화면 깨짐, 느림 | 다음 기능 사이클 |
등급은 **사용자 영향**으로 정한다(내가 얼마나 놀랐는지가 아니라).

## 4. 대응 순서 (SEV1·2)
1. **멈추기 먼저, 원인은 나중**: 직전 배포면 롤백(`npx wrangler rollback`), 아니면 점검 모드·기능 끄기.
2. 서비스 화면·공지 채널에 한 줄 ("○○가 안 되고 있어요, 고치는 중. ○시에 다시 알려 드릴게요").
3. 원인 찾기: 로그(요청 ID) → 최근 변경 → 외부 서비스 상태.
4. 고치고 확인: 스모크·E2E 다시 → 공지 "해결".
5. 48시간 안에 사후 분석.

## 5. 사후 분석 (`docs/incidents/YYYY-MM-DD-<요약>.md`) — 누구 탓이 아니라 구조를 고친다
```
# <요약> (SEV2, 2026-10-03)
- 영향: 누가 · 얼마나 · 몇 분 (예: 목록 화면 5xx, 약 40분, 방문 약 120회)
- 타임라인: 알게 된 시각(어떻게) → 멈춘 시각 → 해결 시각
- 원인: 기술 원인 + 왜 미리 못 잡았나 (테스트·점검의 빈틈)
- 한 일 / 할 일: 재발 방지 1~3개 — 각각 담당·기한. 가장 좋은 것은 "자동으로 잡히게" (테스트·점검·경보 추가)
- 오류 예산 사용: 0.1% (이번 달 누적 0.3% / 0.5%)
```
재발 방지 항목은 PROJECT.md "기능 사이클"이나 AI 회사 tasks 로 넘긴다.
