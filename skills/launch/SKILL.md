# Launch — 출시

목표: **알맞은 사람에게 닿게 하고**, 출시일을 사고 없이 넘기고, 반응을 **다음 행동**으로 바꾼다.

## 입력
- `docs/idea.md` (대상 사용자·고유 가치 제안·채널), `docs/spec.md` (핵심 지표)
- 스테이징·운영 URL 또는 테스트 빌드, guard 통과 결과

## 세부 단계

### L1. 사용성 테스트
`references/user-testing.md` 1절. 대상 사용자 5명, 과제 기반. 치명 문제는 출시 전 수정.

### L2. 비공개 베타
`references/user-testing.md` 4절.
- 규모: 20~100명. 앱은 TestFlight / Play 비공개 테스트(개인 계정은 요건 확인), 게임은 Steam Playtest·Discord.
- 기간: 1~3주. 활성화율·D1/D7 재방문·오류율을 본다.
- 피드백 채널 하나, 버그 신고 양식, 베타 사용자에게 변경 알림.

### L3. 랜딩·스토어 페이지
`references/landing-copy.md`. 헤드라인 = 고유 가치 제안. 전환 측정(UTM·이벤트).
게임은 Steam "Coming Soon" 페이지를 출시 전 충분히 일찍 연다(위시리스트).

### L4. 출시 계획·채널별 게시글
`references/launch-channels.md` 에서 대상 사용자가 있는 채널 3~5개 선택, 채널별로 따로 쓴다. D-14 ~ D+7 일정표.
AI: 게시글·예상 질문 답변·보도자료 초안. 사람: 게시·답글.

### L5. 출시 준비 점검 (Go / No-Go)
`references/launch-readiness.md` 를 출시 전날 확인한다. 하나라도 "No-Go" 항목이 걸리면 미룬다.

### L6. 출시일 운영
같은 파일의 "출시일 운영" 절차. 모니터링 대시보드를 열어 두고 댓글·오류에 바로 대응한다.

### L7. 출시 회고 (D+7)
- 채널별 방문·가입·활성화·결제, 오류·장애, 받은 피드백 요약
- 잘된 것 / 안된 것 / 다음에 바꿀 것
- 피드백을 grow R6 로드맵 후보로 넘긴다.

## 산출물
- `docs/launch.md`: 테스트·베타 결과, 채널 계획·일정표, Go/No-Go 결과, 회고
- 랜딩 페이지·스토어 문구, 채널별 게시글 초안

## 완료 조건
- [ ] 사용성 테스트 5명, 치명 문제 수정
- [ ] 베타 진행, 활성화율·오류율 기록
- [ ] 랜딩·스토어 페이지 공개, 전환 측정 중
- [ ] Go/No-Go 통과 후 공개 출시
- [ ] 회고 작성, 피드백이 로드맵 후보로 넘어감

## 원칙
- 가짜 후기·조작된 수치·업보트 품앗이 금지. 채널 규칙 위반이고 신뢰를 잃는다.
- 광고성 메시지는 수신 동의자에게만 (guard).
- 출시일에 새 기능을 배포하지 않는다. 버그 수정만.
