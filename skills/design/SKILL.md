# Design — 디자인

목표: 명세(spec)를 **사용자가 헤매지 않는 화면**으로 만들고, 구현이 그대로 가져다 쓸 **토큰·컴포넌트·시안**을 남긴다.

## 입력
- `docs/spec.md` (스토리·정책·상태), `docs/idea.md` (대상 사용자)
- **PROJECT.md "디자인 도구 계획" 절** — 단계마다 그 표의 명령만 실행한다(다시 판단하지 않음, 없으면 pilot 2-1 로 먼저 만든다). 기준: `references/design-routing.md`
- 사용자가 좋아하는 레퍼런스 서비스 2~3개 (없으면 묻는다)

## 세부 단계

### D0. 디자인 방향
- 도구 계획의 D0 칸대로: frontend-design 원칙 / `/impeccable shape`(시안 수는 예산 모드) / brandkit 키 아트 / 없으면 `references/design-direction.md`.
- 결과는 `docs/design.md` 맨 앞 "방향" 한 장: 쓰는 장면 한 문장, 색 4~6개(이름·hex), 글꼴과 역할, 레이아웃 한 문장, 기억에 남을 한 가지. D3 토큰은 이 값으로 채운다.
- 외부 스킬은 그 명령의 참고 문서만 읽는다(예: impeccable `reference/shape.md`).

### D1. 사용자 여정·화면 흐름
- 스토리마다 "목표를 이루기까지의 단계"를 적는다.
- **첫 실행 → 첫 가치 경험(aha moment)** 까지 단계 수를 센다. 회원가입은 가능하면 가치 경험 **뒤로**.
- 화면 목록과 이동 관계를 Mermaid 로 그린다. 딥링크·공유 링크로 들어오는 경로도 포함.

### D2. 와이어프레임
- 화면마다 저해상도 구조(영역·요소·우선순위)를 만든다.
- `references/screen-states.md` 의 **상태별 화면**을 빠짐없이 정의한다. 운영 품질은 여기서 갈린다.

### D3. 디자인 토큰·컴포넌트
- `references/design-tokens.md` 구조로 토큰을 정의한다 (라이트·다크). 값은 **D0 방향에서** 가져온다 — 그 파일의 값은 예시일 뿐.
- 컴포넌트 목록: 버튼(주/보조/위험/비활성/로딩), 입력(기본/포커스/오류/비활성), 카드, 목록 항목, 모달·시트, 토스트, 빈 상태, 스켈레톤.
- 각 컴포넌트의 상태(hover·focus·pressed·disabled·loading)를 정한다.

### D4. 핵심 화면 시안
- 핵심 화면 3~5개를 토큰만 쓰는 HTML 로 만든다. 모바일(375px) 기준, 데스크톱도 확인.
- 실제 같은 데이터로 채운다 (긴 이름, 0개, 1000개 같은 극단값 포함).
- 게임: HUD, 메인 메뉴, 일시정지·설정, 결과 화면 우선.
- Playwright **스크립트**로 라이트·다크·모바일·데스크톱 스크린숏을 한 번에 찍어 검토한다 (겹침·줄바꿈·대비). 검증 횟수는 예산 모드(절약 1회, 표준 2회). 도구 계획의 D4 칸에 `critique` 가 있으면 그다음에 1회.
- **좁은 화면 실측 (필수)**: 구현이 생긴 뒤 폭 360~390px 캡처를 한 번 더 찍는다. 데이터는 목록의 **모든 줄 상태**(비어 있음·남의 것·내 것·긴 이름)를 한 화면에 섞는다. 캡처를 사람 눈으로 보듯 확인: 한 줄의 버튼이 두 줄로 밀리지 않나, 짧은 글자(이름·상태)가 줄바꿈되지 않나. 한 줄에 버튼이 3개 이상이면 자주 쓰는 하나만 남기고 "⋯"로 접는다. 테스트(E2E·usertest)는 통과해도 이 문제를 못 보는 경우가 많다 — usertest 자동 점검 "버튼 줄바꿈"이 일부만 잡는다.
- **자동 모드에서도 D4 를 건너뛰지 않는다.** "구현 화면으로 대체"는 금지 — 시안 HTML 과 캡처(`design/shots/`)가 있어야 완료. 자체 검토 뒤 "사람 확인 대기"로 진행한다.

### D5. 프로토타입 테스트
- 시안을 클릭 가능한 프로토타입(링크 연결 HTML)으로 묶는다.
- 대상 사용자 3~5명에게 과제 2~3개를 시켜 본다 (`../launch/references/user-testing.md` 방법). 구현 전에 고치는 게 가장 싸다.

### D6. 접근성 점검
도구 계획의 D6 칸(예: `/impeccable audit`, 없으면 체크리스트). `references/accessibility-checklist.md` 결과표를 남긴다. 대비는 **계산해서** 확인한다.

### D7. 브랜드 에셋
도구 계획의 D7 칸대로 (brandkit 은 **이미지 생성용 프롬프트**를 `design/assets/brand-prompt.md` 에 쓰고 사람이 이미지 생성기에서 만든다 — 없으면 Claude 가 SVG 로 직접). `references/brand-assets.md` 규격으로 앱 아이콘, 파비콘, OG 이미지, 스토어 그래픽을 준비한다.

## 산출물
- `docs/design.md`: 여정, 화면 흐름, 상태별 화면 표, 컴포넌트 목록, 테스트 결과, 접근성 점검표
- `design/tokens.css` (또는 스택에 맞는 토큰 파일), `design/mockups/*.html`, `design/assets/`

## 완료 조건
- [ ] 방향 한 장(D0) — 토큰이 그 값을 쓴다
- [ ] 스토리 전부 화면 흐름에 포함
- [ ] 화면별 상태(빈·로딩·오류·권한 없음·오프라인) 정의
- [ ] 토큰(라이트·다크)·컴포넌트 상태 정의, 대비 기준 통과
- [ ] 핵심 화면 시안 HTML + 캡처 (자동 모드 포함, 건너뛰기 없음)
- [ ] 좁은 화면(360~390px) 실측 캡처 — 버튼 줄바꿈·짧은 글자 줄바꿈 없음
- [ ] 프로토타입 테스트 3명 이상, 치명 문제 반영
- [ ] 접근성 체크리스트 통과
- [ ] 브랜드 에셋 규격별 준비

## 원칙
- 디자인 스킬은 사람에게 보이는 결과물(D0·D4·D6·D7)에만. D1·D2·D3 문서·D5 계획에는 쓰지 않는다.
- 한 화면에 핵심 행동(Primary 버튼)은 하나.
- 장식보다 **위계**(크기·굵기·여백)로 중요도를 보여 준다.
- 파괴적 행동(삭제·결제)은 확인 단계 또는 되돌리기.
- 타사 브랜드·로고를 흉내 내지 않는다. 폰트·아이콘·이미지 라이선스를 기록한다(guard G5 재확인).
