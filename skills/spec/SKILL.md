# Spec — 기획

목표: "무엇을 만들지"를 **모호함 없이** 정한다. 구현 중 막히는 질문의 대부분은 여기서 답이 나와 있어야 한다.
명세가 없으면 AI 도 사람도 "그럴듯하지만 운영하면 깨지는" 코드를 만든다.

## 입력
- `docs/idea.md` (MVP Must 기능, 사업성, 중단 기준)

## 세부 단계

### S1. 사용자 스토리·수용 기준
`references/prd-template.md` 형식으로 Must 기능마다 작성한다.
- 스토리: "**[역할]** 로서 **[목표]** 를 하고 싶다, **[이유]** 때문에."
- 수용 기준: Given / When / Then. **실패·경계 경우**를 최소 2개 포함한다.
- 수용 기준은 그대로 E2E 테스트가 된다 (build B10). 스토리마다 ID(F1, F2 …)를 붙이고 **테스트 이름에 그 ID 를 쓴다** — `scripts/trace.mjs` 가 테스트 없는 기능을 잡는다(요구사항 추적).

### S2. 기능 정책
기능마다 아래를 표로 정한다. 운영 중 사고는 대부분 여기서 비어 있던 칸에서 난다.
- **권한**: 누가 보고·만들고·고치고·지울 수 있나 (본인 / 공유받은 사람 / 관리자 / 비로그인)
- **상태**: 객체의 상태와 전이 (예: 초안 → 공개 → 삭제됨). 삭제는 소프트 삭제인가?
- **예외**: 네트워크 끊김, 외부 API 실패, 중복 요청, 동시 수정, 빈 결과
- **한도**: 사용량 한도(요청 수·저장 용량·파일 크기), 무료/유료 차이. 비용이 드는 외부 호출은 반드시 한도
- **데이터 보존**: 탈퇴 시 무엇을 언제 지우나
- **설정 변경**: 규칙·가격 같은 설정이 바뀌면 과거 기록은 어떻게 되나 (당시 값 스냅숏 vs 재계산)
- **신원 모델**: 계정 / 계정 없음(비밀 링크·토큰) / 기기 토큰 중 무엇인가. 계정 없는 모델이면 링크 유출·분실·재발급 정책을 정한다

### S3. 데이터 모델
`references/data-model.md` 로 엔터티·관계·필드·인덱스를 정의한다.
- ERD 를 Mermaid 로 그린다.
- 개인정보 필드에 표시한다 (guard G3 에서 그대로 쓴다).

### S4. 아키텍처·외부 연동
`references/architecture.md` 로 정한다.
- 구성도(클라이언트·서버·DB·외부 서비스), 요청 흐름 1~2개.
- 외부 서비스마다: 용도, 요금·무료 한도, 장애 시 폴백, 키 관리 위치.
- 주요 결정은 ADR(결정 기록) 한 단락씩 남긴다.

### S5. 비기능 요구
같은 파일의 "비기능 요구" 표를 채운다: 응답 시간, 가용성 목표, 동시 사용자, 데이터 보존, 월 비용 상한, 지원 기기·브라우저.
1인 개발 기준 **현실적인 숫자**로 정한다 (예: 가용성 99.5%, 주요 화면 p95 1초 이내).
월 비용 상한의 기본값은 **0원(무료 등급)**. 무료 한도(요청·DB 읽기/쓰기·저장)를 예상 사용량으로 나눠 여유를 계산하고 `docs/costs.md` 에 남긴다 (`../build/references/free-tier.md`).

### S6. 분석 이벤트 설계
`references/analytics-events.md` 로 핵심 지표를 측정할 이벤트를 정한다. 출시 후에 추가하면 이전 데이터가 없다.
- **추적 계획 표**(이벤트 · 언제 · 속성 · 지표) — 이벤트 이름은 백틱으로. idea 의 가정 성공 기준과 북극성 지표를 이 이벤트로 잴 수 있어야 한다.
- 구현 뒤 `scripts/events-check.mjs` 로 계획과 코드를 대조한다(계획에만 있으면 출시 뒤 숫자가 비고, 코드에만 있으면 아무도 모르는 숫자가 쌓인다).

### S7. 마일스톤·작업 분해
- Must 기능을 **수직 슬라이스**(화면~API~DB 까지 한 번에 동작하는 단위)로 나눈다.
- 각 작업은 반나절~2일 크기. 순서: 기반 → 인증 → 가장 위험한 기능 → 나머지.
- 마일스톤 3개 정도: M1 내부 동작, M2 베타 가능, M3 출시 가능.

### S8. 대표용 한 장 요약
`docs/spec.md` 맨 위에 **"한 장 요약"** 절: 대표가 3분 안에 읽고 동의할 수 있게 쉬운 말로.
- 만드는 것 (Must 5개 이하, 한 줄씩 "사용자가 ○○할 수 있다")
- **안 만드는 것** (이번에 뺀 것과 이유) — 대표가 기대한 게 빠졌는지 여기서 드러난다
- 사람이 할 일·돈이 드는 것, 예상 완성 시점
- 대표에게 묻는 질문(있으면 3개 이하)
대표가 동의하면(자동 모드면 "대표 확인 대기") 2단계 완료.

## 게임이면 추가
`references/game-design.md` 로 코어 루프, 진행·보상, 경제(재화 흐름), 난이도 곡선, 콘텐츠 분량을 정한다.

## 산출물
- `docs/spec.md`: 스토리·수용 기준, 정책 표, 비기능 요구, 이벤트 표, 마일스톤
- `docs/architecture.md`: 구성도, 데이터 모델, 외부 연동 표, ADR
- (게임) `docs/game-design.md`

## 완료 조건
- [ ] Must 기능마다 스토리 + 실패 경우 포함 수용 기준
- [ ] 기능마다 권한·상태·예외·한도 정의
- [ ] ERD 와 개인정보 필드 표시
- [ ] 외부 서비스별 폴백·비용 한도
- [ ] 비기능 요구 숫자 확정 (월 비용 상한·무료 한도 여유 포함)
- [ ] 핵심 지표 이벤트 정의
- [ ] 작업 목록이 반나절~2일 단위로 분해됨
- [ ] 대표용 한 장 요약(만드는 것·안 만드는 것) (S8)

## 원칙
- 모르는 것은 추측으로 채우지 말고 **질문 목록**으로 남겨 사용자에게 묻는다.
- 명세는 짧게. 표와 목록 위주. 구현 중 바뀌면 명세도 같이 고친다.
