# 테스트 전략

1인 개발은 모든 걸 테스트할 수 없다. **깨지면 가장 아픈 곳**부터.

## 무엇을 어느 층에서
| 층 | 대상 | 비중 |
|---|---|---|
| 단위 | 계산·변환·검증·정책 로직 (가격, 한도, 상태 전이) | 많이, 빠르게 |
| 통합 | API + DB + 권한, 외부 API 어댑터(모킹) | 핵심 엔드포인트 전부 |
| E2E | spec 수용 기준의 핵심 흐름 (가입 → 핵심 행동 → 결제) | 3~10개 |
| 스모크 | 운영 배포 직후 핵심 페이지·헬스체크 | 자동 |

## 반드시 테스트할 것
- [ ] 권한: 다른 사용자 리소스 접근이 막힌다
- [ ] 한도: 초과 시 차단·안내
- [ ] 결제: 웹훅 처리·중복 수신·실패
- [ ] 외부 API 실패 시 폴백
- [ ] 탈퇴 시 데이터 처리
- [ ] 마이그레이션이 빈 DB 와 기존 DB 모두에서 적용된다

## 원칙
- 외부 API 는 테스트에서 호출하지 않는다 (모킹). 키 없는 환경에서 테스트가 통과해야 한다.
- 버그를 고칠 때는 **실패하는 테스트를 먼저** 쓴다.
- 불안정한(flaky) 테스트는 끄지 말고 원인을 고친다.
- 게임: 로직(데미지 계산·경제·저장/불러오기)은 단위 테스트, 재미는 플레이테스트.

## 수동 점검 (출시 전)
- [ ] 실제 기기: iOS·Android 각 1대, 저사양 기기 1대
- [ ] 브라우저: Chrome·Safari (모바일 Safari 포함)
- [ ] 느린 네트워크(3G 시뮬레이션), 오프라인
- [ ] 다크 모드, 큰 글씨
