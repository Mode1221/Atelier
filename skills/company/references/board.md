# 업무 보드 규칙 (GitHub Issues)

모든 부서는 GitHub Issues 로 일을 주고받는다. 대시보드(Atelier HQ)도 이 규칙으로 화면을 그린다.

## 라벨
| 라벨 | 뜻 |
|---|---|
| `dept:ceo` `dept:plan` `dept:design` `dept:dev` `dept:qa` `dept:security` `dept:marketing` `dept:support` `dept:ops` `dept:data` | 담당 부서 (하나만) |
| `status:todo` | 할 일 (라벨이 없어도 할 일로 본다) |
| `status:doing` | 진행 중 |
| `status:review` | 다른 부서 검토 중 (보통 QA·보안) |
| `approval-needed` | **대표 결재 대기** |
| `approved` / `rejected` | 대표가 승인 / 반려 |
| `ops-alert` | 정기 점검 실패 (checkup) |

완료 = 이슈 닫힘.

## 결재 요청 형식
결재가 필요한 부서는 이슈에 `approval-needed` 를 붙이고 아래 형식으로 댓글을 단다. 대시보드는 **첫 줄 요약**과 **종류**를 그대로 보여 준다.
```
[결재 요청] <한 줄 요약 — 개발을 모르는 사람도 이해할 말로>
종류: 배포 | 공개 게시 | 지출 | 법률 | 기타
금액: <지출이면 원 단위, 아니면 없음>
승인하면: <무슨 일이 일어나는지>
반려하면: <무슨 일이 일어나는지>
자세히: <링크·첨부>
```

## 부서 간 전달
- 새 일을 만들 때: 제목은 결과로("가입 버튼이 안 눌리는 문제 고치기"), 본문에 배경·완료 조건, 담당 `dept:` 라벨.
- 다른 부서에 넘길 때: `dept:` 라벨을 바꾸고 무엇을 넘기는지 댓글.
- 개발 결과는 PR 로. PR 본문에 `Closes #번호`. QA 가 PR 을 검토한다.

## 금지
- 대표 결재 없이: 운영 배포, 외부 공개 게시, 돈이 드는 일, 약관·처리방침 게시, 사용자 데이터 삭제.
- 다른 부서 이슈를 말없이 닫기.
