# 목표·로드맵 자동 계획 (대표실)

대표실(ceo)이 매일 아침 이 절차로 **서비스에 맞는 목표와 로드맵을 만들거나 갱신하고, 오늘 할 일을 부서에 나눠 준다.** 대표는 목표·로드맵을 직접 쓰지 않는다 — 본부 "목표" 탭에서 보고, 단계 전환만 결재한다.
경로는 모두 `companies/<SERVICE>/` 아래다.

## 1. 데이터
`plan/roadmap` (한 문서):
```json
{
  "stage": "6 출시 — 공개 베타",
  "focus": "이번 2주의 한 문장 목표",
  "goals": [ { "id": "g1", "text": "베타 사용자 모으기", "metric": "주간 기록 모임", "target": 10, "current": 3, "unit": "개", "due": "2026-10-13", "source": "metrics/main 또는 측정 없음" } ],
  "items": [ { "id": "r1", "title": "대학 커뮤니티 홍보", "why": "g1", "dept": "marketing", "status": "now", "stage": "launch L4", "done": false } ],
  "updatedAt": "…", "reviewAt": "다음 전체 재검토 날짜", "history": ["2026-09-30 처음 만듦", "…"]
}
```
- `status`: `now`(이번 주) · `next`(다음) · `later`(나중) · `done`. `now` 는 3~5개.
- `dept`: 부서 ID, 사람만 할 수 있으면 `human`.
- `current` 는 **측정값만**. 없으면 `null` + `source: "측정 없음"` — 숫자를 지어내지 않는다.

서비스 문서 `companies/<SERVICE>` 에서 쓰는 값: `name`, `summary`(한 줄 설명), `audience`(대상 사용자), `kind`(웹/앱/게임), `stage`, `url`.

## 2. 언제 새로 짜나 (전체 재작성)
- `plan/roadmap` 이 없다 (첫 실행)
- 서비스 `stage` 가 roadmap 의 `stage` 와 다르다 (단계가 바뀜)
- `reviewAt` 이 지났다 (기본 2주마다)
- 목표를 달성했거나 기한이 지났다
- 사용자 의견·지표가 계획을 뒤집을 만큼 달라졌다 (예: 같은 불편 5건 이상, 활성화율 급락)

그 외에는 **갱신만**: 끝난 항목 `done`, `current` 값 새로 고침, `next` → `now` 당기기, `history` 에 한 줄.

## 3. 새로 짜는 법
1. `playbook/stages`(Atelier 8단계와 게이트)에서 지금 단계와 **다음 단계로 가는 게이트**를 찾는다.
2. **목표 2~4개**: 게이트를 숫자로 바꾼 것. 서비스 종류·단계별 기본값(아래 표)에서 출발해 서비스에 맞게 고친다.
3. **로드맵 항목 6~12개**: 목표마다 그 목표를 움직이는 일. 아래 표의 단계별 일감에서 고르고, 사용자 의견·지표·실패 보고에서 나온 일을 더한다. 각 항목에 담당 부서.
4. 측정할 수 없는 목표가 있으면 "측정 만들기" 항목(dev/data)을 `now` 에 넣는다.
5. `focus` 한 문장, `reviewAt` = 오늘 + 14일.

### 단계별 기본 목표·일감
| 단계 | 목표 예 | 일감 예 (담당) |
|---|---|---|
| 1 아이디어 | 인터뷰 5명, 경쟁 3곳 조사 | 경쟁 조사(plan), 인터뷰 질문(plan), 인터뷰 진행(human) |
| 2 기획 | 핵심 스토리·수용 기준 확정 | 명세(plan), 데이터 모델(dev) |
| 3 디자인 | 핵심 화면 시안, 접근성 통과 | 시안(design), AI 사용성 테스트(qa) |
| 4 구현 | 운영 준비 체크리스트 통과 | 기능(dev), 테스트(qa), 배포 자동화(ops) |
| 5 보안·법률 | 치명 이슈 0, 처리방침 게시 | 보안 점검(security), 약관(security) |
| 6 출시·베타 | 주간 활성 단위 10, 의견 20건, 활성화 40% | 채널 홍보(marketing), 올리기(human), 의견 분류(support), 막힌 곳 고치기(dev/qa) |
| 7 운영 | 가동률 99.5%, 오류 0 유지 | 점검(ops), 백업 확인(ops), 문의 응답(support) |
| 8 성장 | 주간 활성·재방문 증가, 실험 1개/2주 | 퍼널 분석(data), 실험(plan/dev), 로드맵 재정렬(ceo) |
게임이면 플레이테스트·위시리스트, 앱이면 스토어 등록·심사를 해당 단계에 더한다.

## 4. 매일 나눠 주기
1. `now` 항목마다 열린 `tasks`(todo/doing/review) 가 없으면 하나 만든다: `tasks/<dept>-<YYYYMMDD>-<짧은이름>`, `by: "ceo"`, `detail` 에 왜(목표)와 끝 조건. `dept == human` 이면 `human` 에.
2. 하루에 새로 만드는 일은 **5개까지**. 같은 일을 두 번 만들지 않게 먼저 조회한다.
3. 담당 부서의 예약이 꺼져 있거나 없으면(`companies/<SERVICE>.routines`) 보고에 "○○ 부서가 꺼져 있어 □□ 일이 멈춰 있어요" 라고 적는다. 대표가 부서 탭에서 켤 수 있다.
4. 3일 넘게 `doing` 인 일은 다시 `todo` 로 돌리고 보고에 적는다.

## 5. 단계 전환
지금 단계의 게이트가 채워지면 `approvals` 에 kind "단계 전환" 으로 올린다 — 무엇이 채워졌는지, 다음 단계에서 무엇을 하는지 쉬운 말로. **승인되면** 서비스 문서의 `stage` 를 바꾸고 다음 실행에서 로드맵을 새로 짠다. 대표가 반려하면 이유를 목표에 반영한다.

## 6. 보고 (`reports/ceo`)
한두 문장: 오늘 나눈 일 수, 가장 중요한 목표의 진행(측정값이 있을 때만 숫자), 대표가 할 일·결재 수. 로드맵을 새로 짰으면 "로드맵을 새로 짰어요 — 목표 탭" 이라고.
